# B-08 安全机制

- **一句话结论**：Safety 是 harness 从"demo"到"生产"的门槛——核心是**隔离（沙箱）+ 审批（权限/HITL）+ 审计（可见性）**三件套；2026 年安全重心从"拒绝有害输出"转向"防 prompt injection 与越权工具调用"。

## 四类安全机制

| 机制 | 解决什么 | 实现 | 权衡 |
|---|---|---|---|
| **沙箱隔离** | 恶意/失控代码执行 | 容器（Docker）、云沙箱（E2B/OpenSandbox/Daytona）、K8s、本地受限（Bubblewrap/Apple Container） | 隔离↑ 灵活性↓ 启动延迟↑ |
| **权限审批** | 越权工具调用 | 规则引擎（ALLOW/REJECT/REQUIRE_CONFIRM）、人工确认流（HITL）、bypass 模式 | 审批↑ 效率↓；"确认疲劳"是真实问题 |
| **审计可见性** | 出错时可追溯 | 全量 trace、provenance-aware 决策审计、中间件观测 | 审计↑ 成本↑；生产 agent 必须可解释 |
| **输入/注入防护** | prompt injection、工具投毒 | 内容过滤、来源标记、敏感操作二次确认 | 过滤↑ 误伤↑ |

## 关键设计决策（五维的 Safety 维度）

1. **审批流**：哪些工具必须确认？（文件写/删除、shell、外部网络）；规则怎么配（AgentScope PermissionRule）
2. **隔离级别**：进程内（快）/ 容器（标准）/ 远程（云）——2026 趋势是"intermediate isolation（沙箱+权限提示）"为主流，高保证审计（provenance-aware）仍罕见
3. **审计**：事件流是否完整落盘？工具调用的输入输出是否留痕？谁在什么上下文里批准了什么？
4. **bypass 模式**：无人工介入的端到端自治（AgentScope PermissionMode bypass）——信任度与效率的交换

## HITL（Human-in-the-Loop）的两种形态

- **确认式 HITL**：工具执行前要人点头（REQUIRE_CONFIRM → RequireUserConfirmEvent → 暂停 → UserConfirmResultEvent 恢复）——AgentScope/OpenAI guardrails 形态
- **审批式 HITL**：动作已做但影响大，事后人审（企业合规）——Microsoft Agent Framework 的 approval handling 形态

## 2026 安全焦点（迁移点）

- **间接 prompt injection 已成研究热点**（如 arXiv 2608.16393 对 DeepSeek Harness 的注入评估）：agent 读取外部文档/网页时，内容中隐藏指令可劫持工具调用。
- 防线：来源标记（AgentScope HintBlock 的 source）、工具白名单、敏感动作隔离、读取与执行分离。
- 学习任何 harness 先问：**它的默认权限模式是什么？工具在什么环境执行？事件可审计吗？**

## 与 AgentScope 的对照

- `PermissionEngine` + `PermissionRule` + `PermissionDecision`（ALLOW/REJECT/REQUIRE_CONFIRM）+ `PermissionMode`
- 沙箱：`WorkspaceBase`（local/Docker/E2B/K8s/OpenSandbox/…）+ 内置工具（Bash/Edit 等）默认在沙箱内执行
- 审计：`TracingMiddleware`（OpenTelemetry）+ 事件流
- HITL：`AskUser` 工具 + `RequireUserConfirmEvent`/`UserConfirmResultEvent`
